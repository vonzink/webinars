# Prompt 01 — Webinar Builder

Use to build a **new** webinar in this house style, or to rebuild a module from
scratch. Replace everything in `[BRACKETS]`.

---

```
You are building a premium educational webinar for a mortgage audience. This is
not a sales presentation. The test it must pass: the audience leaves saying
"I finally understand this," not "I sat through another pitch."

## PRESENTER
Zach Zink, Mortgage Loan Originator, Mountain State Financial Group — independent
mortgage broker, Colorado. Also builds mortgage software and educational tools.
Core belief: educating borrowers creates trust. Does not use pressure sales.

## AUDIENCE
[WHO — age, situation, what they already know, what they're afraid of]

## TOPIC
[TOPIC]

## RUNTIME
[N] minutes taught, plus [N] minutes live Q&A.

## NON-NEGOTIABLE DESIGN RULES

1. ONE CANONICAL EXAMPLE. Pick one scenario — one property, one loan, one set of
   numbers — and carry it from the first module to the last. Every module adds a
   layer to the SAME numbers. Never introduce a second example. Fluency comes from
   repetition against a fixed reference, not from variety. Write the canonical
   example to its own file first, before any slide.

2. ORDER BY THE AUDIENCE'S FEARS, NOT BY TOPIC. Ask what they are actually
   afraid of and sequence around that. Topic order is the lender's mental model
   and it is why mortgage content feels like a pitch.

3. EVERY MODULE ENDS IN A PORTABLE ARTIFACT — a rule, a threshold, or a checklist
   they can execute without the presenter. Understanding decays. Procedures don't.

4. NAME THE OBJECTIONS OUT LOUD, including at least two that cut AGAINST the
   presenter's financial interest. Pre-empting an objection is worth ~10x
   answering it later.

5. NO URGENCY. No "rates are going up," no scarcity, no countdown, no deadline.
   Include an explicit early slide promising this, so breaking it would be visible.

6. TEACH WITH THE TOOLS, DON'T PITCH THEM. Any calculator or tool appears DURING
   the teaching, inside the confusion it resolves — never as a closing segment.

7. VALUE BEFORE ASK. Homework and downloads come before the call to action, and
   the downloads are ungated. No email capture.

8. EVERY STATISTIC CARRIES SOURCE + YEAR + A VERIFY FLAG. Anything unverifiable
   gets a directional phrasing or gets cut. Build every core argument so it
   survives without a precise figure.

## REQUIRED OUTPUT

- Master outline with minute-by-minute run of show
- Module files, each with: beat sheet, spoken script, visual direction,
  transitions in and out, compliance notes, and failure modes
- One file per slide: purpose, headline, graphic, animation, speaker notes,
  references, compliance
- Minimum one story per module — named character, one specific sensory detail,
  one number, one turn, ≤45 seconds, moral NOT explained (the next slide is the
  moral)
- Polls, with at least two DIAGNOSTIC polls where a wrong answer is the setup for
  the teaching moment
- Written exercises the audience does live
- Homework, downloads, and a TIERED call to action — the smallest tier must cost
  the audience nothing and require nothing
- Declared compression points ([CUT-n]) and expansion points ([EXP-n]) so the
  talk survives live timing slippage
- Printed checkpoint times for mid-stream recovery

## PROCESS — DO NOT SKIP

Draft the outline. Then critique it hard, in writing, as if reviewing someone
else's work. Then revise. Then critique AGAIN, this time asking "where does this
break in a live room?" Then revise again. Keep every critique pass as an artifact
so the reasoning is recoverable later.

Only after the third pass do you write slides.

## VOICE
Plain language. Define every term the first time it is spoken, in under 10 words.
Say numbers out loud, don't only show them — half the audience watches the replay.
Say the uncomfortable thing. Warm, direct, occasionally funny. Never smug about
jargon the audience doesn't know — the jargon is the industry's fault, not theirs.
```

---

## Notes on using this prompt

- **The process section is the whole prompt.** Skipping the critique passes
  produces a competent table of contents. See `versions/v1/CRITIQUE-v1.md` for what
  a first draft looks like before it gets torn apart.
- Write the canonical example **first**. Every consistency bug in a deck like this
  traces to inventing numbers per module.
- The rule against a second example is the one people break most. Don't.
